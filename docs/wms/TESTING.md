# Test tiers and honest status

| Tier                              | Entry point                                                                           | Network/data                                                           | Result meaning                                                                                 |
| --------------------------------- | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Foundation                        | `node --test tests/foundation/*.test.mjs` and `node scripts/wms/foundation-check.mjs` | Files only, no DB/provider                                             | Phase catalog/templates/guardrails work; no WMS behavior claim                                 |
| Existing local unit/UI/static SQL | `bun test ./tests/*.test.ts`                                                          | Synthetic inputs, no production credentials                            | Current 91 declared tests; SQL text assertions are NOT migration/RLS execution                 |
| Type/build/lint                   | `bunx --no-install tsc --noEmit`, `bun run build`, `bun run lint`                     | Synthetic build env only; install from existing bun.lock               | Each result recorded separately; baseline failures not hidden or relabeled as pass             |
| Disposable DB integration         | `node scripts/wms/db-check.mjs` (P01 implementation required)                         | Loopback disposable Supabase-compatible PostgreSQL, synthetic fixtures | Must apply actual migrations and test transactions/RLS in separate sessions; currently BLOCKED |
| Full core acceptance              | `docs/wms/acceptance/SCENARIOS.md` + adapter implementation in P01–P07                | Synthetic DB and fake provider transport using actual domain code      | Nine core scenarios plus phase extensions; not executed by foundation                          |
| Live read-only                    | `node scripts/wms/live-check.mjs` (future approved runner)                            | Explicit approved account allowlist, no production mutation            | Currently deliberately BLOCKED, independent of local/DB success                                |

CI local jobs run on pushes/PRs with read-only contents permissions, no secrets, persist-credentials false, pinned action commits and timeout limits. DB workflow is manual-only and uses a disposable service with a hardcoded non-production fixture credential. The DB runner rejects non-loopback URLs and currently stops with exit2 until P01 implements real tests. A running PostgreSQL service alone is not a test pass.

Live testing has its own manual workflow with no secrets wired. It fails closed instead of silently passing a skipped job. Implement it only after the owner approves read scope, provider allowlist and evidence handling; require an independently protected environment before giving it live credentials. A typed approval reference is not proof of approval. No workflow contains merge, deploy or provider write commands.

Manual `workflow_dispatch` needs the workflow file to exist on the default branch. These new manual workflows are prepared on the draft branch and may not be dispatchable from the UI until a separately approved integration. Do not merge into main merely to make a button appear. Local invocation remains available for foundation checks; live invocation remains blocked. [GitHub documentation](https://docs.github.com/actions/managing-workflow-runs/manually-running-a-workflow).

GitHub environment required reviewers only enforce review when actually configured; secrets become available after review and protection rules pass. Self-review/admin-bypass settings require deliberate owner configuration. This PR does not create a protected environment or assume one exists. [GitHub documentation](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/review-deployments).

## Baseline handling

Do not fix widespread existing formatting or refactor business code just to green CI. Record inherited lint/build/type failures as blockers on the exact baseline and open a narrowly scoped follow-up. Dependency installation problems, runner assignment failures and unavailable DB/provider adapters are NOT successful verification. Never set continue-on-error on acceptance jobs. Always retain separate job results and redacted logs.
