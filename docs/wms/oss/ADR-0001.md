# ADR-0001 — Proposed modular OSS WMS core

Date: 2026-10-21 UTC. Status: **PROPOSED / CONDITIONAL — awaiting owner approval; implementation blocked**.

## Decision requested

Recommend option **1: adopt Tryton as the stock/workflow foundation with separate Surooh extensions**, subject to the blocking validation gates below. This recommendation does not replace the current system, approve migration or claim production readiness. Retain existing Surooh source intact while evaluating. No Codex task is authorized by this ADR.

Tryton is preferred because native company-scoped movements and receiving/dispatch/transfers exist, actual 8.2 runtime tests exercised them, and the native product_kit module implements component semantics. This reduces the amount of WMS workflow we would own while allowing Marketplace, Accounting and SAM to remain independent. InvenTree's actual API/model experiments expose material tenant and virtual-sales-kit adaptation costs. ERPNext and Odoo remain credible broader ERP challengers; they were inspected, not runtime-tested, so a globally proven superiority claim is not justified.

## Alternatives

1. **OSS core + Surooh extensions (recommended conditionally).** Tryton owns physical moves and assignments; Surooh owns offer identity, channel normalization, explicit reservation commands and versioned integration facade. A kit's independently calculated available quantity is not a shared multi-offer budget. Prohibit force assignment and implement/test all-or-nothing component reservation in the reviewed adapter; do not silently replace native semantics.
2. **Keep current + OSS libraries/components.** Lowest UI/database transition, but libraries do not supply missing persisted WMS workflows. InvenTree component reuse is feasible under MIT after dependency/license review, yet transplanting Django models into the TypeScript/Supabase ledger is not a small library addition. Remains fallback if OSS integration/security gates fail. No component is approved for integration by this PR.
3. **Continue entirely current.** Preserve proven domain-specific bol/identity logic; full receiving, picking, inspection and transfers still need implementation and native DB proof. Current code has not demonstrated better WMS maturity than the OSS candidates. Therefore option 3 is not supported as a superiority conclusion.

## Mandatory gates before accepting the choice

- G1: Rebuild Tryton on disposable PostgreSQL; independent sessions race for one last shared component and cannot both reserve. Exercise shortage rollback across all BOM lines, deterministic locks, retry/replay, cancel/dispatch races and reconciliation. Current SQLite successes do not close G1.
- G2: Two restricted users, two companies: direct/list/report/export/worker contexts cannot cross-read or mutate; test company switching, stale membership and cross-company product/location/move IDs. Company quantity context alone does not close G2.
- G3: Full two-native-kit sale-to-component flow, cancellation, quarantine inspection, transfer conservation, append-only correction evidence and duplicate provider-event inbox. Disable/deny native bypass/force-assignment paths. The upstream kit scenario uses force assignment for its demonstration; it is not no-oversell proof.
- G4: Exact support/LTS choice, SBOM/advisories, distribution license decision, API contract/upgrade/backup rehearsal and owner-reviewed measured TCO. Re-evaluate Odoo/ERPNext in a database-capable sandbox if Tryton fails a hard gate or owner favors broader ERP operations.
- G5: Explicit owner acceptance of the ADR and a separately reviewed rebased phase plan; explicit phase-start authorization afterward. PR/Issue closure, CI green or this document cannot supply approval.

## Architecture boundaries

Keep current TypeScript UI and read-only bol ingestion behind a versioned service facade. Map Surooh IDs to Tryton company/product/location/move IDs. Maintain a single authoritative stock writer; never dual-write Supabase and Tryton reservations. New Surooh modules add durable inbox/outbox, idempotent command records, BOM snapshots, company-bound authorization and audit export. Accounting financial documents remain owned by Surooh Accounting; any unavoidable internal Tryton accounting reference data must be mapped without duplicate financial postings. SAM receives scoped summaries/delegation, not raw ORM credentials.

## Consequences, migration and reversal

Positive: reuse established operational workflows and tests; retain channel/UI investment; avoid rebuilding a full ERP. Costs: Python operational expertise, adapter ownership, security hardening, GPL distribution analysis and upgrades. Risks: force-assignment bypass, incomplete native kit reservation semantics, accounting coupling and identity drift. These remain blocking rather than estimated away.

Only after approval: synthetic schema mapping and read-only export rehearsal, then reviewed migration with movement provenance and opening-balance reconciliation. Never migrate offer balances by summing shared EAN stock. No real data migration is included now. Reversal at this stage is simply closing the research PR; no application/schema rollback is necessary. Later cutover rollback requires quiesced writers, reconciled event watermark and a reviewed restore/replay plan, not switching two live ledgers back and forth.
