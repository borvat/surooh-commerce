# تقرير التقييم الهندسي المستقل — Surooh WMS

النتيجة المقترحة: **الخيار ١ — Tryton كأساس للمخزون ودورات المستودع، مع إضافات Surooh مستقلة**. القرار مشروط وغير معتمد، ولا يسمح باستبدال النظام أو تشغيل Codex. النظام الحالي محفوظ بالكامل.

## ما أُنجز فعلياً

- فحص كود Surooh ومقارنته مع ERPNext وOdoo Community وTryton وInvenTree وOpenBoxes بإصدارات ومراجع محددة، مع فصل الوظائف المنفذة عن الوظائف غير المثبتة.
- إعداد مقارنة للبيانات وواجهات API وعزل الشركات والأمان والتراخيص وإعادة استخدام كود Lovable/Replit والتكاملات والتكلفة المفترضة لثلاث سنوات.
- تشغيل نموذجين حقيقيين معزولين لـTryton وInvenTree، بقواعد SQLite مصطنعة وباستخدام منطق المشروعين الأصلي وعميل API الأصلي داخل العملية. ليست محاكاة حسابية بديلة أو واجهة إنتاج مستضافة.
- Tryton: ٣٥ اختباراً/سيناريو ناجحاً. InvenTree: ١١ ناجحاً واختبار تزامن واحد متجاوزاً بسبب المحرك. بعض الاختبارات تثبت وجود فجوة مع متطلباتنا، وليس نجاح تلك المتطلبات.
- توثيق ADR وخطة P00 قبل المراحل التسع، مع مهام وتبعيات واختبارات وشروط بدء وانتهاء ومخاطر وتراجع لكل مرحلة.
- إضافة بوابة تمنع انتقال المرحلة إلى المراجعة إذا غاب اعتماد القرار أو أدلة G1–G4. نجاح الاختبارات لا يمنح صلاحية التنفيذ أو الدمج أو النشر.

## لماذا Tryton مبدئياً؟

دورات مخزون فعلية وعزل رصيد بحسب الشركة وباقات أصلية، مع قابلية فصل نواة WMS عن الأنظمة الثلاثة الأخرى. يمكن الاحتفاظ بواجهة Surooh ومنطق هوية المنتجات وbol المقروء فقط عبر طبقة تكامل. InvenTree قوي في الأصناف وBOM وترخيصه MIT، لكن نموذج الشركات فيه يمثل العملاء والموردين، وتخصيص مكوّن لسطر بيع باقة لا يحدث تلقائياً. Odoo وERPNext بدائل ERP قوية؛ لم تُشغّل نماذجهما هنا، لذلك لا يوجد ادعاء بأن Tryton تفوّق عملياً على الجميع.

## ما بقي محجوباً أو غير مثبت

- التزامن على PostgreSQL؛ Docker غير متاح ولم يكتمل إعداد محرك PostgreSQL محلي. SQLite لا يثبت أقفال الإنتاج. التجاوز ظاهر في النتائج.
- عزل API والتقارير والتصدير بين مستخدمين مقيدين لشركتين؛ اختبار سياق الشركة ليس برهاناً كافياً.
- دورة بيع باقتين أصليتين متنافستين كاملة، والفحص قبل إعادة المرتجع للبيع، ومنع مسارات فرض التخصيص أو الحجز الجزئي غير المسموح به.
- تكرار أحداث القنوات وAccounting وSAM على مستوى عقود Surooh، وفحص الثغرات والتبعيات والدعم والترخيص والتكلفة بقياسات فعلية.
- قواعد حماية GitHub وتشغيل Actions كانت محجوبة في فحص الأساس السابق؛ لا يوجد إثبات جديد بأنها أصبحت مفعّلة أو أن CI البعيد نجح.

## ما يحتاج قرارك

مراجعة التوصية والسماح باستكمال أدلة الاعتماد في بيئة قواعد بيانات معزولة مناسبة، أو طلب اختبار Odoo/ERPNext منافس قبل الاختيار. اعتماد نهائي للأساس يتطلب إغلاق G1–G4 ثم موافقتك الصريحة على SHA والخطة المعدلة. تشغيل Codex لكل مرحلة يحتاج موافقة مستقلة لاحقاً. لا يوجد استبدال أو ترحيل أو دمج أو نشر إنتاجي ضمن هذه الأعمال.

كل التفاصيل والسجلات في هذا المجلد؛ تقديرات التكلفة افتراضات هندسية وليست عروض أسعار. لا دليل كافياً لإعلان نجاح جميع اختبارات قبول Surooh أو اكتمال التقييم الإنتاجي النهائي.
