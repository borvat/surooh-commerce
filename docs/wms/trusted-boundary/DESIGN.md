## DB-F01 protocol

One transactional command function, `surooh_boundary.submit_order`, checks current company membership, admin/warehouse role, owner-configured source grants and source channel policy **before returning any replay**. HTTP company/source originate in a verified token and must agree with the body. Direct SQL source selection is restricted by owner-managed source grants. `fixture-bol` requires a company-owned channel; `fixture-manual` explicitly allows an absent channel. No silent default source/channel.

Permanent command primary key = `(company_id, source_id, request_id)`. Source and request strings are required and bounded. Server-produced canonical JSONB includes operation, ordered lines/quantities, channel, warehouse and note. SHA256 plus JSONB equality detect a conflicting replay (HTTP409); request clients cannot supply a trusted fingerprint. Different array order is conservatively a different command. Valid duplicate = original stored JSON result (`order_id`), not a new effect or a unique-index error.

The command insert, native reservation/order call and stored response commit in one transaction. ON CONFLICT + row lock serializes independent connections. Failure rolls back command and stock together; a committed command survives HTTP response loss/process death and can be replayed. Authorization revoked since the first call denies replay. This is exactly-once **database effect for this command**, not exactly-once network delivery, power-loss durability or arbitrary external providers. No command-retention/delete API exists; a future retention policy must preserve deduplication over the full replay horizon.

The original `place_order` body remains unchanged but EXECUTE is revoked for application roles. D18 now exercises the protected entrypoint; H14 proves raw bypass denied. The original raw function is not claimed idempotent. D15 keeps its original zero-foreign-row expectation. Native legacy `external_ref` stores `surooh:` plus a hash of the command key to prevent cross-source collision with the historical channel/ref unique index. Original request identity remains in command metadata. **Existing UI external-reference display/import mapping is not wired**; that requires a separately approved integration slice.

## DB-F02 trusted identity

A real loopback HTTP service verifies HS256 JWTs using pinned PyJWT; issuer, audience, signature, required exp/iat/nbf/sub/jti/company/source are checked. Revocation is a durable `(issuer,jti)` table consulted on every authenticated request. Role claims never select SQL roles; current DB memberships/source grants decide authorization. Revocation blocks subsequent requests; it does not promise cancellation of an already executing transaction.

SQL service `trusted_wms_http` is a distinct restricted LOGIN, neither superuser nor BYPASSRLS. Only this trusted login may supply per-transaction JWT identity GUCs after verification. Tokens do not expose its random credential. Fixed parameterized routes expose product reads and protected order submission only; no SQL/config/raw RPC endpoint. A queue pool resets claims before and after every transaction, including denials/errors; leaked contexts close the connection. One-connection alternating-company tests and two-connection concurrent tests exercise actual backend PIDs. Explicit company predicates prevent an actor with membership in two companies from widening a company-scoped HTTP read.

Untrusted direct SQL is a **different identity model**: separate LOGIN credentials mapped in an owner-protected table to a subject using immutable `session_user`. auth.uid/auth.jwt ignore client-changeable claims for those logins, even in SECURITY DEFINER functions. SET ROLE to the HTTP login and SESSION AUTHORIZATION are denied. SECURITY DEFINER functions fix search_path to pg_catalog and fully qualify tables/functions. The driver owner alone configures mappings, grants, source policies and revocations; no public administration API is added. Do not grant the trusted service login to application users.

Threat boundary: theft of trusted SQL credentials, owner/superuser access, host compromise or ability to replace service code defeats this model. Protect credentials, networking, process/file identities and issuer provisioning before real integration. This candidate does not install PostgREST or prove deployed Supabase parity. HS256 synthetic issuer has no production TLS/JWKS/key rotation/identity-provider integration; stdlib HTTP is a test boundary, not a production gateway.
